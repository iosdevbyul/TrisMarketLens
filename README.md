# Tris Market Lens

Research-driven market intelligence UI for DonghakStockVision.

## Stack

- Next.js
- React
- TypeScript
- Tailwind CSS
- Vitest

The web repository owns presentation and frontend data contracts. DonghakStockVision
remains responsible for market data, research logic, evidence, model artifacts,
backtesting state, snapshot export, and the read-only FastAPI transport.

## Current architecture

```text
TrisMarketLens
  -> DataSource
      -> MockDataSource
      -> HttpDataSource
          -> DonghakStockVision FastAPI
              -> validated research-api-snapshot.json
```

Mock mode remains the default so the UI can run independently. HTTP mode connects
the same UI to the reviewed DonghakStockVision snapshot.

## Run locally

Opening http://localhost:3000 does not start the app by itself. A local Next.js
development server must be running on the same computer first.

Requires Node.js 22.

For a fresh local checkout:

```bash
git clone https://github.com/iosdevbyul/TrisMarketLens.git
cd TrisMarketLens
cp .env.example .env.local
npm install
npm run dev
```

For an existing checkout:

```bash
git switch main
git pull
cp .env.example .env.local
npm install
npm run dev
```

Then open:

- http://localhost:3000
- http://localhost:3000/api/health

## Mock mode

Default local mode:

```text
MARKET_LENS_DATA_SOURCE=mock
DONGHAK_API_BASE_URL=http://127.0.0.1:8000
MARKET_LENS_URL=http://127.0.0.1:3000
```

The backend URL is ignored while the mode is `mock`.

## Real-data E2E mode

The real-data path uses a snapshot explicitly generated by DonghakStockVision.

### 1. Generate the backend snapshot

From the DonghakStockVision repository:

```bash
git switch main
git pull
python -m pip install -e '.[api]'

dsv-api-export \
  --root . \
  --market-db .data/market.sqlite3 \
  --output .data/research-api-snapshot.json
```

The exporter is read-only and refuses to overwrite an existing snapshot. When you
intentionally regenerate it, remove or archive the previous generated snapshot
first.

### 2. Start DonghakStockVision FastAPI

Still in the DonghakStockVision repository:

```bash
dsv-api --snapshot .data/research-api-snapshot.json
```

The default backend address is:

```text
http://127.0.0.1:8000
```

Check:

```text
http://127.0.0.1:8000/api/v1/health
```

### 3. Switch Tris Market Lens to HTTP mode

In TrisMarketLens, set `.env.local` to:

```text
MARKET_LENS_DATA_SOURCE=http
DONGHAK_API_BASE_URL=http://127.0.0.1:8000
MARKET_LENS_URL=http://127.0.0.1:3000
```

Then start Next.js:

```bash
npm run dev
```

### 4. Verify the complete connection

With both servers running:

```bash
npm run verify:http
```

The verifier checks the backend health and key research endpoints, verifies that
the stock list count matches the published universe, checks one stock-detail
response, and finally confirms that Tris Market Lens itself reports a healthy HTTP
backend connection.

### 5. Audit backend/web feature readiness (local operator only)

With both **locally running** servers and `MARKET_LENS_DATA_SOURCE=http`, run:

```bash
npm run verify:integration:audit
```

This is a separate **real HTTP, GET-only** audit. It checks the backend's immutable
health, project/research coverage, models, evidence, blocked baseline, stock list,
operational catalog, runs, freshness, alerts, screener; it then checks the web's
health, operational catalog count parity, and six server-rendered pages.

The JSON result distinguishes:

- `available`: a response with a recognized contract, **not** research approval.
- `empty`: a valid response with no records.
- `unconfigured`: optional backend publication returned HTTP 503.
- `failed`: transport, shape, parity, or web render failure.

The CLI returns a failure exit status for partial or failed coverage. An operator
must inspect each `checks` entry before claiming end-to-end real-data readiness.
It never writes to the backend, executes models, trades, or substitutes demo
records. The backend's `read_only` health response does **not** prove that
optional publications are available or data is approved for investment.

`npm run verify:next-queue` executes **offline fixture tests** of this audit
alongside other script checks. CI passing those fixtures is *not* proof that
an operator's private loopback backend or real market data were available.
A live audit is possible only when both services are actually running locally.

`/api/health` returns HTTP 503 in HTTP mode when the backend is missing,
misconfigured, unreachable, or returns an unexpected health payload. The frontend
does not silently fall back to mock data.

## Integrated research evidence path

Open `/research-path` from the sidebar or the overview. Optionally select a
six-character ticker to follow the existing **read-only** feature path:

1. Collected, unreviewed KRX snapshot (`/operational-market`)
2. Published research universe and stock identity (`/stocks/[ticker]`)
3. Global model validation/OOS artifacts (`/models`)
4. Explicit ticker publication evidence (`/research-workbench?ticker=...`)
5. Research lifecycle and source blockers (`/evidence`)
6. Pinned historical portfolio results and comparisons (`/backtesting/portfolios`)
7. Recorded acquisition, scheduler and alert trace (`/operations/trace`)

Each stage reports its own source status: `observed`, `empty`,
`unavailable`, `blocked`, or `demo`. An observed stage means records were
returned; it **never** indicates an approved market prediction, verified
point-in-time validity, broker execution or investment suitability. Model-wide
metrics and the ticker's published `modelId` remain distinct identities.

In HTTP mode, optional API 503s and transport failures remain unavailable;
they are not replaced with demonstration values. In mock mode the entire
path is clearly marked as fictional. Historical report comparison selections
are retained when returning from the comparison view.

Unit/contract tests cover URL validation, source separation, missing or
unconfigured services, research blockers, demo safety, and the navigation
path. CI verifies build and offline fixtures, **not** a live operator-owned
market backend. Run `npm run verify:integration:audit` only with an actually
running loopback backend and web server to test live HTTP integration.

## Current routes

- / research overview
- /stocks searchable stock explorer
- /stocks/[ticker] stock detail and OHLC/evidence integration surface
- /models qualified model overview
- /models/[direction] model qualification, validation/OOS metrics, configuration, and artifact provenance
- /evidence evidence-layer overview and baseline-freeze blockers
- /evidence/[layer] calendar, settlement, DART, security-lifecycle, and corporate-action evidence details
- /backtesting backtest overview and run-readiness gate
- /backtesting/baseline locked baseline contract, chronology, policy, and performance placeholders
- /api/health frontend/backend connection health

The UI does not execute models, signals, evidence collection, or backtests and
does not present simulated performance as real research output.

Evidence pages preserve scope boundaries. A verified market-wide calendar or
settlement layer does not imply that per-security lifecycle or corporate-action
coverage is complete. Open research blockers stay visible and fail closed.

The baseline backtest page exposes the already-locked policy and chronology only.
The signal anchor ends on 2025-06-30. Execution-only sessions may resolve pending
entries and open positions afterward without generating new signals, followed by
the settlement tail. Performance fields remain empty until the immutable run is
actually executed.
